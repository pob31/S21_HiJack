# S21_HiJack Audit — 2026-04-27

## Executive summary

S21_HiJack is a mature ~25.7k LOC async Rust daemon that bridges a DiGiCo S21/S31 mixing console with iPads, monitor apps, and QLab via OSC. The build is **clean** (`cargo check --all-targets` passes), unit-test coverage is **strong** (286 tests), and the code is well-structured around clear module boundaries. The main risks lie not in correctness of individual modules but in **operational hygiene**: the show file write is non-atomic so a crash mid-save can corrupt the operator's work, the Mode 3 iPad proxy auto-learns its destination from the first packet (a real concern even on a closed network), and several locks are held across `.await` network sends — fine on a quiet show, but a stalled console can wedge the gang/monitor pipeline. The trust model is *closed-LAN by design* — the monitor and trigger listeners are intentionally unauthenticated to allow operator workflows like swapping a musician's device mid-show; the audit recommends interface binding and optional CIDR filtering rather than per-device secrets. The toolchain hygiene is weak: no CI, no `rustfmt.toml`, no `[lints]` table, no `cargo audit`, and 509 sites are flagged by `cargo fmt --check`. None of this is shipping-blocking on its own — but together they form a substantial pre-release hardening backlog.

### C2 — Monitor server is unauthenticated [Medium / Security] — **DOWNGRADED 2026-04-27**

**Location:** [src/osc/monitor_server.rs:240-246](../src/osc/monitor_server.rs#L240-L246), [src/console/monitor_engine.rs:60-67](../src/console/monitor_engine.rs#L60-L67).

**Status:** Downgraded from Critical to Medium 2026-04-27 after operator discussion. The original recommendation (per-device HMACs / connection tokens) directly fights the device-swap workflow (musician's tablet runs out of battery → grab a phone → reconnect under the same client name from a new IP). On a closed IEM-VLAN deployment that workflow is the more important property, and per-device secrets are over-engineering for the actual threat model. Replaced the original recommendation with a lighter network-layer mitigation below.

**Observation:** Client identity is the string between `/monitor/` and the next `/` in the OSC path:

```rust
let rest = path.strip_prefix("/monitor/")?;
let (name, action) = rest.split_once('/')?;
// ...
let client_name = name.to_string();
```

`MonitorEngine::handle_command` looks up that name in `MonitorManager` and applies the client's `permitted_auxes` / `visible_inputs`. The reply address is the inbound packet's `src`; `manager.update_last_seen(&client_name, reply_addr)` rebinds the address on every received packet.

**Threat model (deployment intent):** the monitor server runs on a dedicated IEM/musician VLAN that the venue router segments from the public/guest networks. Every endpoint on that VLAN is operator-controlled (band-issued tablets/phones). The "attacker" the design needs to handle is *not* a malicious LAN peer but a **mis-configured** peer (wrong subnet, stale config, cross-talk between rigs).

**Residual risk after the recommended mitigation:** a host on the IEM VLAN that is on the operator's allowed subnet but mis-configured can still impersonate any client by name. The operator accepts that — the device-swap UX win outweighs it.

**Recommendation (revised):**
1. **Bind monitor-server socket to a specific interface.** The infrastructure already supports this via `create_bound_udp_socket(_, interface_name)` — surface it in the setup-tab UI for the monitor port (the GP OSC and iPad sockets already expose interface selection). When set, the daemon won't accept monitor packets on the FOH/control LAN at all.
2. **Optional CIDR allowlist on the daemon.** One or more `--monitor-allow-cidr 192.168.10.0/24` flags (and corresponding setup-UI fields). Daemon drops packets whose `src` is outside the allowed ranges. Doesn't care which device sends within the range — devices swap freely. Default: empty allowlist = accept everything (current behavior).
3. **Log `src` IP on every `/monitor/*/connect`.** Already partially done at [src/console/monitor_engine.rs:68](../src/console/monitor_engine.rs#L68); confirm the log is at `info!` so the operator can audit "who connected as Drummer" in the running session log.
4. **Document the threat model.** Add a short paragraph to the README under "Deploying" explaining the closed-LAN assumption and recommending VLAN segmentation.

**Effort:** S (1–2 h for interface-binding UI + CIDR filter + log review). README update separate.

### C3 — Show file save was non-atomic [Critical / Reliability] — **RESOLVED 2026-04-27**

**Location:** [src/persistence/show_file.rs](../src/persistence/show_file.rs).

**Status:** Resolved 2026-04-27. `ShowFile::save` now writes to `<path>.tmp`, fsyncs, and renames over the destination. On rename failure the orphan `.tmp` is best-effort removed. Added test [`save_is_atomic_and_leaves_no_tmp_file`](../src/persistence/show_file.rs) that saves twice with different content and asserts (a) the destination contains the second version and (b) no `.tmp` file remains. All 327 tests pass.

**Original observation:** the previous `save()` called `tokio::fs::write(path, json)` directly, which opens the destination with truncation. The file is empty between truncate and final flush. A crash, kill, or power-cycle in that window left the show file empty or partial.

**Original impact:** the show file is the only persistent representation of the operator's snapshots, cues, macros, palettes, monitor profiles, and gangs. Losing it mid-show is a worst-case outcome. Hard crashes during save are rare but real (memory pressure, kernel panic, accidental power-off of a Pi).

**Implementation notes:**
- Tmp filename is built by appending `.tmp` to the full path (`<path>.tmp`), preserving the original extension. Avoids the `Path::with_extension("json.tmp")` form which would silently rewrite an unrelated user-chosen extension (`myshow.txt` → `myshow.json.tmp`).
- The atomic-replace works the same way on Windows (`MoveFileExW(MOVEFILE_REPLACE_EXISTING)`) and Unix (`rename(2)`).
- Parent-directory `fsync` (Unix-only durability under power-loss) is *not* implemented. `tokio` doesn't expose it directly, and for a music-rig daemon on a Pi the rename-only guarantee is enough — the next save writes a fresh tmp file regardless.

### H1 — Mode 3 auto-learns iPad IP when unpinned [Low / Security] — **RESOLVED 2026-04-27**

**Location:** [src/console/ipad_connection.rs:251-255](../src/console/ipad_connection.rs#L251-L255).

**Status:** Resolved 2026-04-27. The audit's original framing overstated the severity. **Remaining recommendations (Low priority):**
- README note that production deployments should pin `ipad_ip` in the show file. Folded into [L4](#l4--readme-drift-low--documentation).
- Defer to **H9** to delete the more-permissive dead `IpadForwarder` code path.

### H2 — Gang engine holds write lock across network sends [High / Concurrency]

**Location:** [src/console/gang_engine.rs:79-159](../src/console/gang_engine.rs#L79-L159) (`process_gang_update`), called from [src/console/connection.rs:300-307](../src/console/connection.rs#L300-L307).

**Observation:** `process_gang_update` is `&mut self`. The caller in `connection.rs::process_message` holds `gang_engine.write().await` for the entire body of `process_gang_update`. Inside that body, for each gang, for each target channel, the engine awaits `self.send_to_console(&target_addr, &target_value)` — a real UDP send that can block if the socket is buffer-full or the kernel queue is contended. The state mirror is also locked (`state.read().await` on line 133, `state.write().await` on line 152) under the gang_engine write.

**Impact:** Every parameter update on a member of any gang serializes the whole gang fan-out behind a single network send. While the gang engine is locked, no other code can call its methods (including any future caller — the surface is currently small but this would surprise anyone adding a UI hook). More importantly, while `state.write()` is held inside the gang loop, *every* read or write of the state mirror across the daemon waits — the snapshot engine, the macro learn-mode recorder, the monitor poll loop, the iPad mirror, and the UI update task. A console that briefly drops UDP throughput stalls the entire daemon.

**Recommendation:** Two independent improvements:
1. **Drop gang_engine lock around `send_to_console`.** Take it only to mutate `suppression_set`, then release before the network send. The suppression set's invariants tolerate a small pre-insert window.
2. **Drop `state.write()` before `send_to_console`.** Compute the new value, drop the lock, send, then re-acquire to update the mirror. Or, more invasively, make the state update happen via an event channel processed by a single owner task (no lock at all).

Add a benchmark that measures end-to-end fan-out latency under a synthetic 100ms send delay before/after.

**Effort:** M (2–4 h with tests).

### H3 — Monitor engine writes state after sending to console [High / Concurrency]

**Location:** [src/console/monitor_engine.rs:222-238](../src/console/monitor_engine.rs#L222-L238), [src/console/monitor_engine.rs:421-431](../src/console/monitor_engine.rs#L421-L431).

**Observation:** In `forward_send_change` and `handle_aux_change`, the daemon sends the new parameter to the console first, then updates the local state mirror:

```rust
if let Err(e) = self.sender.send(&path, args).await {
    warn!(%addr, "Monitor: failed to send to console: {e}");
    return false;
}
// Also update local state mirror
self.state.write().await.update(addr, value.clone());
```

If the send to the console succeeds but the daemon is killed before the write, the state mirror is briefly behind the console. More concerning: if the send is slow, *another* event arriving (e.g., a poll-and-push tick) reads stale state and pushes that stale value to other clients. The window is small but real (UDP send + scheduler delays).

**Impact:** Race condition where other monitor clients can be told the *old* value briefly after the FOH operator changes it via a client, until the state mirror is updated. Worst case: a flicker on a competing client's UI; no audio impact.

**Recommendation:** Either update state *before* sending (optimistic mirror, with rollback on send failure — preferred for sub-second responsiveness), or wrap state-update + send in a sequenced task ownership pattern. The optimistic path matches what the gang engine does (line 152) and is a one-line move.

**Effort:** S (30 min).

### H4 — `raw_proxy_loop` writes state on every packet [High / Concurrency]

**Location:** [src/console/ipad_connection.rs:221](../src/console/ipad_connection.rs#L221), [src/console/ipad_connection.rs:285-324](../src/console/ipad_connection.rs#L285-L324).

**Observation:** In Mode 3, every packet (in either direction) goes through `log_and_capture_packet`, which best-effort-parses it and, if it's a parameter update, calls `state.write().await.update(...)` and (if changed) `dirty_tracker.write().await.mark(addr)`. This runs on the *forwarding hot path*: every packet from the console must be parsed and the state lock must be acquired before the packet is forwarded to the iPad — though the forward itself happens before the parse, so packet latency is unaffected.

But the key observation: the iPad protocol is chatty. The console emits frequent meter / parameter updates, and during snapshot recalls each parameter change is a separate packet. State write-lock contention here can ripple into the rest of the daemon (snapshot engine, gang engine, UI) under load.

**Impact:** Probably fine on a quiet show; can stutter under load (e.g., loading a session with many channels). No correctness issue, but visibility/UI staleness is possible.

**Recommendation:**
1. Skip state-update entirely for high-frequency meter messages (already done — `MeterValues` branch is separate, but other parameter floods aren't filtered).
2. Move state-update off the proxy hot path: forward bytes immediately, then enqueue the parsed message to a single state-owner task that drains the queue without holding cross-engine locks.
3. Or: sample/throttle — mirror at most one update per parameter per N ms.

**Effort:** M (2–4 h).

### H5 — Trigger listener is unauthenticated [Medium / Security] — **DOWNGRADED 2026-04-27**

**Location:** [src/osc/trigger_listener.rs:65-96](../src/osc/trigger_listener.rs#L65-L96), [src/osc/trigger_listener.rs:125-161](../src/osc/trigger_listener.rs#L125-L161).

### H6 — iPad path parser accepts any 0..=255 channel number [High / Input validation]

**Location:** [src/model/channel.rs:102-122](../src/model/channel.rs#L102-L122).

**Observation:**

```rust
pub fn from_ipad_path(path: &str) -> Option<(Self, &str)> {
    // ...
    let num: u8 = num_str.parse().ok()?;
    let channel = match channel_type {
        "Input_Channels" => ChannelId::Input(num),
        "Aux_Outputs" => ChannelId::Aux(num),
        "Group_Outputs" => ChannelId::Group(num),
        // ...
    };
    Some((channel, rest))
}
```

`num` is unconstrained except by `u8` — `Input(255)` parses fine even though valid inputs are 1..=60. Same for every other channel type. The same pattern exists in `extract_u8` for GP OSC parser inputs.

**Impact:** Internally-stored "channels" with out-of-range numbers — no immediate panic, but downstream code may misbehave: HashMap lookups silently miss, snapshot recall produces unexpected encode results, the iPad proxy may forward bogus addresses to the console (which presumably ignores them, but we're trusting that). A malformed packet from a malicious or buggy peer pollutes the `ConsoleState` with junk channels.

**Recommendation:** Validate at parse time using the active `ConsoleConfig`. The GP OSC path *does* this via `from_gp_osc_number_with_config` — port the same pattern to `from_ipad_path`:

```rust
pub fn from_ipad_path_with_config(
    path: &str,
    config: &ConsoleConfig,
) -> Option<(Self, &str)> {
    // ... parse type and num as today, then:
    let valid = match channel_type {
        "Input_Channels" => (1..=config.input_channel_count).contains(&num),
        "Aux_Outputs" => (1..=config.aux_output_count).contains(&num),
        // ...
    };
    if !valid { return None; }
    // ...
}
```

This also has a defense-in-depth benefit if the iPad proxy is ever exposed to untrusted networks.

**Effort:** S (1 h).

- Subtle behavioral difference: `IpadForwarder` *replaced* `ipad_addr` whenever a new source arrived. If anyone had wired `IpadListener` in by accident, they would have re-introduced a worse version of H1.
- Hidden by the project-wide `#![allow(dead_code)]` (M3) — clippy/rustc would otherwise have flagged this.

**Why "comment out → build → if clean delete" wasn't useful here:** the project-wide `#![allow(dead_code)]` (see M3) suppresses warnings on the definitions, so a clean build with the code commented out wouldn't tell us anything. The signal we wanted is "compiler errors when the symbols are gone" — i.e. just delete and build. Grep first to scope the blast radius, `git restore` if anything goes wrong.

### H10 — `ParameterPath::Gain` ambiguity [High / Correctness] — **RESOLVED 2026-04-27**

**Location:** [src/model/parameter.rs](../src/model/parameter.rs).

**Status:** Resolved 2026-04-27. Split into `TotalGain` (GP OSC `total/gain`, post-fader+CG sum) and `AnalogGain` (iPad `Channel_Input/analog_gain`, mic preamp). The wire protocols stay exactly as DiGiCo defines them — only the internal data model gains a second variant. Added 9 tests covering encode/parse round-trip, iPad path absence, GP OSC path absence, legacy `"Gain"` alias migration, section/continuity/availability/timing-category. All 340 tests pass.

**What was actually wrong (sharper than the original framing):** while reading the code I found that GP OSC `total/gain` was *not parsed at all* in `from_gp_osc_suffix`. The previous `Gain` variant must have mapped to it, but when `Gain` was renamed to `AnalogGain` (with the iPad parser added in Phase 6), the GP OSC mapping was dropped entirely. Every total-gain change the console emitted was being silently ignored — worse than ambiguity, the data was just lost. The split now restores GP OSC `total/gain` parsing and routes it to its own variant.

**Implementation notes:**
- `#[serde(alias = "Gain")]` is on `TotalGain`, not `AnalogGain`. Pre-Phase-6 snapshot files where `"Gain"` always meant GP OSC `total/gain` migrate to the correct physical knob.
- `TotalGain.to_ipad_suffix()` returns `None`; `AnalogGain.to_gp_osc_suffix()` returns `None`. Each variant has exactly one wire path on exactly one protocol.
- `TotalGain` is input-only via `available_for_channel`, lives in `ParameterSection::InputGain`, is_continuous, has no `TimingCategory` (instant recall, like `AnalogGain`).

**Out of scope for this fix (deliberately):**
- `macros_tab.rs::ParameterChoice` does not yet expose `TotalGain` as a user-pickable macro target. Adding it is a separate UX decision and can be done at any time.

### M8 — No timeouts on `.await` lock acquisitions or sends [Medium / Reliability]

**Location:** Project-wide — every `state.write().await`, `state.read().await`, `sender.send().await`, `socket.send_to().await`.

**Observation:** A stalled lock holder (e.g., the gang-engine fan-out under H2) can block all other tasks indefinitely. A blocked UDP send (kernel buffer full + non-responsive receiver) can hang a state-update path.

**Recommendation:** Wrap the most contentious sites with `tokio::time::timeout`. Pick budgets that distinguish "console is slow" (1 s) from "console is wedged" (10 s). On timeout, log and continue rather than hang. The fan-out in `gang_engine::send_to_console` is the highest-priority target.

**Effort:** M (2–3 h, plus tuning).

### M9 — `OscLog` is a single mutex [Medium / Concurrency]

**Location:** [src/model/osc_log.rs:52](../src/model/osc_log.rs#L52) (per Explore agent finding).

**Observation:** Every OSC message logged goes through `Arc<Mutex<OscLogInner>>`. At high traffic (Mode 3 proxy) this serializes every send/receive across the daemon.

**Recommendation:** Switch to a bounded MPSC channel + a single consumer task that owns the inner state. UI reads via a snapshot/clone. This is a small refactor, but only worth doing if profiling shows the lock is hot.

Then `connect_from_parts(sender, rx, state: DaemonState, cancel)`. This isn't a behavior change — it's just bookkeeping. Removes most of the suppressions.
