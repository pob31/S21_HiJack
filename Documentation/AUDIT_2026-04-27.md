# S21_HiJack Audit — 2026-04-27

## Executive summary

S21_HiJack is a mature ~25.7k LOC async Rust daemon that bridges a DiGiCo S21/S31 mixing console with iPads, monitor apps, and QLab via OSC. The build is **clean** (`cargo check --all-targets` passes), unit-test coverage is **strong** (286 tests), and the code is well-structured around clear module boundaries. The main risks lie not in correctness of individual modules but in **operational hygiene**: the show file write is non-atomic so a crash mid-save can corrupt the operator's work, the Mode 3 iPad proxy auto-learns its destination from the first packet (a real concern even on a closed network), and several locks are held across `.await` network sends — fine on a quiet show, but a stalled console can wedge the gang/monitor pipeline. The trust model is *closed-LAN by design* — the monitor and trigger listeners are intentionally unauthenticated to allow operator workflows like swapping a musician's device mid-show; the audit recommends interface binding and optional CIDR filtering rather than per-device secrets. The toolchain hygiene is weak: no CI, no `rustfmt.toml`, no `[lints]` table, no `cargo audit`, and 509 sites are flagged by `cargo fmt --check`. None of this is shipping-blocking on its own — but together they form a substantial pre-release hardening backlog.

### C2 — Monitor server is unauthenticated [Medium / Security] — **DOWNGRADED & RESOLVED 2026-04-27**

**Location:** [src/osc/monitor_server.rs](../src/osc/monitor_server.rs), [src/model/cidr.rs](../src/model/cidr.rs), [src/persistence/show_file.rs](../src/persistence/show_file.rs).

**Status:** Downgraded from Critical to Medium 2026-04-27 after operator discussion (per-device HMACs fight the device-swap workflow). Then resolved later the same day with the network-layer mitigation:
- New `Ipv4Cidr` utility in `src/model/cidr.rs` — IPv4-only CIDR parser + match, no extra dependency. 9 tests.
- `MonitorServer::start_with_cancel` now accepts an `allowlist: Vec<Ipv4Cidr>`. Empty list = accept all (preserves current behavior). Non-empty = drop packets whose source IP isn't covered. Drops surface as `warn!` at exponentially-spaced thresholds (1, 2, 4, 8, …) so a chatty mis-configured peer doesn't flood logs.
- Interface bind was already plumbed (`create_bound_udp_socket(_, interface_name)`). Now used end-to-end.
- `ConnectionSettings` gained `monitor_allow_cidrs: Vec<String>` (with `#[serde(default)]` for backward compat). `parse_cidr_allowlist` materializes the strings into `Ipv4Cidr`s at startup, logging and skipping invalid entries.
- CLI flag: repeatable `--monitor-allow-cidr 192.168.10.0/24`. Show-file persistence round-trips through the UI's `SetupTabState` (UI editor for the field is a follow-up).
- Source-IP logging on connect was already present (`monitor_engine.rs:68` logs `%reply_addr` on `MonitorCommand::Connect`).

**Observation:** Client identity is the string between `/monitor/` and the next `/` in the OSC path:

```rust
let rest = path.strip_prefix("/monitor/")?;
let (name, action) = rest.split_once('/')?;
// ...
let client_name = name.to_string();
```

`MonitorEngine::handle_command` looks up that name in `MonitorManager` and applies the client's `permitted_auxes` / `visible_inputs`. The reply address is the inbound packet's `src`; `manager.update_last_seen(&client_name, reply_addr)` rebinds the address on every received packet.

**Threat model (deployment intent):** the monitor server runs on a dedicated IEM/musician VLAN that the venue router segments from the public/guest networks. Every endpoint on that VLAN is operator-controlled (band-issued tablets/phones). The "attacker" the design needs to handle is *not* a malicious LAN peer but a **mis-configured** peer (wrong subnet, stale config, cross-talk between rigs).

**Residual risk after the recommended mitigation:** a host on the IEM VLAN that is on the operator's allowed subnet but mis-configured can still impersonate any client by name. The operator accepts that — the device-swap UX win outweighs it.

**Recommendation (revised):**
1. **Bind monitor-server socket to a specific interface.** The infrastructure already supports this via `create_bound_udp_socket(_, interface_name)` — surface it in the setup-tab UI for the monitor port (the GP OSC and iPad sockets already expose interface selection). When set, the daemon won't accept monitor packets on the FOH/control LAN at all.
2. **Optional CIDR allowlist on the daemon.** One or more `--monitor-allow-cidr 192.168.10.0/24` flags (and corresponding setup-UI fields). Daemon drops packets whose `src` is outside the allowed ranges. Doesn't care which device sends within the range — devices swap freely. Default: empty allowlist = accept everything (current behavior).
3. **Log `src` IP on every `/monitor/*/connect`.** Already partially done at [src/console/monitor_engine.rs:68](../src/console/monitor_engine.rs#L68); confirm the log is at `info!` so the operator can audit "who connected as Drummer" in the running session log.
4. **Document the threat model.** Add a short paragraph to the README under "Deploying" explaining the closed-LAN assumption and recommending VLAN segmentation.

**Effort:** S (1–2 h for interface-binding UI + CIDR filter + log review). README update separate.

### C3 — Show file save was non-atomic [Critical / Reliability] — **RESOLVED 2026-04-27**

**Location:** [src/persistence/show_file.rs](../src/persistence/show_file.rs).

**Status:** Resolved 2026-04-27. `ShowFile::save` now writes to `<path>.tmp`, fsyncs, and renames over the destination. On rename failure the orphan `.tmp` is best-effort removed. Added test [`save_is_atomic_and_leaves_no_tmp_file`](../src/persistence/show_file.rs) that saves twice with different content and asserts (a) the destination contains the second version and (b) no `.tmp` file remains. All 327 tests pass.

**Original observation:** the previous `save()` called `tokio::fs::write(path, json)` directly, which opens the destination with truncation. The file is empty between truncate and final flush. A crash, kill, or power-cycle in that window left the show file empty or partial.

**Original impact:** the show file is the only persistent representation of the operator's snapshots, cues, macros, palettes, monitor profiles, and gangs. Losing it mid-show is a worst-case outcome. Hard crashes during save are rare but real (memory pressure, kernel panic, accidental power-off of a Pi).

**Implementation notes:**
- Tmp filename is built by appending `.tmp` to the full path (`<path>.tmp`), preserving the original extension. Avoids the `Path::with_extension("json.tmp")` form which would silently rewrite an unrelated user-chosen extension (`myshow.txt` → `myshow.json.tmp`).
- The atomic-replace works the same way on Windows (`MoveFileExW(MOVEFILE_REPLACE_EXISTING)`) and Unix (`rename(2)`).
- Parent-directory `fsync` (Unix-only durability under power-loss) is *not* implemented. `tokio` doesn't expose it directly, and for a music-rig daemon on a Pi the rename-only guarantee is enough — the next save writes a fresh tmp file regardless.

### H1 — Mode 3 auto-learns iPad IP when unpinned [Low / Security] — **RESOLVED 2026-04-27**

**Location:** [src/console/ipad_connection.rs:251-255](../src/console/ipad_connection.rs#L251-L255).

**Status:** Resolved 2026-04-27. The audit's original framing overstated the severity. Reframed after operator discussion: the trust-on-first-packet behavior on the iPad-side socket is faithful to DiGiCo's underlying protocol (the console authenticates by IP rather than by handshake — same model in both directions), and we can't make our proxy stronger than the protocol it's proxying. Production deployments already have the `--ipad-ip` / setup-tab field to pin the iPad's address explicitly. Added a `warn!` at startup when Mode 3 launches with `ipad_target = None` so the operator notices and either pins the IP or accepts the auto-learn fallback knowingly.

**Why the original High framing was wrong:**
1. The console's iPad protocol is closed-source. We're a man-in-the-middle proxy — we can't add a handshake DiGiCo didn't define.
2. The actually-used path at [src/console/ipad_connection.rs:251](../src/console/ipad_connection.rs#L251) only sets `ipad_addr` when it's `None`. After first-packet wins, the destination cannot be re-targeted by a later sender. This is *stricter* than the underlying DiGiCo protocol's behavior.
3. The closed-LAN deployment model (see C2 / H5) covers the residual risk — iPad VLAN is operator-controlled.

**What about `IpadForwarder`?** The dead-code path at [src/osc/ipad_client.rs:307-312](../src/osc/ipad_client.rs#L307-L312) *does* re-target on every new source — that would be a regression. **H9 calls for deleting that code**, which closes the lingering concern.

**Mitigation applied:**
- Startup warning added in `connect_mode3_proxy`: `"Mode 3: iPad IP not pinned — will auto-detect from first inbound packet. Set --ipad-ip (or the iPad IP field in setup) for production deployments."` Visible in logs at `warn!` level.

**Remaining recommendations (Low priority):**
- README note that production deployments should pin `ipad_ip` in the show file. Folded into [L4](#l4--readme-drift-low--documentation).
- Defer to **H9** to delete the more-permissive dead `IpadForwarder` code path.

### H2 — Gang engine holds write lock across network sends [High / Concurrency]

**Location:** [src/console/gang_engine.rs:79-159](../src/console/gang_engine.rs#L79-L159) (`process_gang_update`), called from [src/console/connection.rs:300-307](../src/console/connection.rs#L300-L307).

**Observation:** `process_gang_update` is `&mut self`. The caller in `connection.rs::process_message` holds `gang_engine.write().await` for the entire body of `process_gang_update`. Inside that body, for each gang, for each target channel, the engine awaits `self.send_to_console(&target_addr, &target_value)` — a real UDP send that can block if the socket is buffer-full or the kernel queue is contended. The state mirror is also locked (`state.read().await` on line 133, `state.write().await` on line 152) under the gang_engine write.

**Impact:** Every parameter update on a member of any gang serializes the whole gang fan-out behind a single network send. While the gang engine is locked, no other code can call its methods (including any future caller — the surface is currently small but this would surprise anyone adding a UI hook). More importantly, while `state.write()` is held inside the gang loop, *every* read or write of the state mirror across the daemon waits — the snapshot engine, the macro learn-mode recorder, the monitor poll loop, the iPad mirror, and the UI update task. A console that briefly drops UDP throughput stalls the entire daemon.

**Recommendation:** Two independent improvements:
1. **Drop gang_engine lock around `send_to_console`.** Take it only to mutate `suppression_set`, then release before the network send. The suppression set's invariants tolerate a small pre-insert window.
2. **Drop `state.write()` before `send_to_console`.** Compute the new value, drop the lock, send, then re-acquire to update the mirror. Or, more invasively, make the state update happen via an event channel processed by a single owner task (no lock at all).

Add a benchmark that measures end-to-end fan-out latency under a synthetic 100ms send delay before/after.

**Effort:** M (2–4 h with tests).

### H3 — Monitor engine writes state after sending to console [High / Concurrency] — **RESOLVED 2026-04-27**

**Location:** [src/console/monitor_engine.rs](../src/console/monitor_engine.rs) (`forward_send_change` and `handle_aux_change`).

**Status:** Resolved 2026-04-27. Both call sites now apply the *optimistic mirror update* pattern: `self.state.write().await.update(...)` is done **before** the network send. Concurrent readers — notably the 20Hz `poll_and_push_state_changes` loop pushing to other clients — observe the operator's intent immediately rather than waiting for the UDP send to round-trip.

The original behavior was actually broken on send failure: it returned without updating state, so the operator's own UI showed nothing happening if the network glitched. The new behavior shows the change locally regardless; if the underlying send fails, the next echo from the console (or a subsequent operator action) heals any discrepancy. UDP `sendto` rarely fails in practice — this is a near-zero-risk tradeoff for a measurable UX win.

The bool return from `forward_send_change` still gates the *immediate* echo to other clients on send success, but other clients also see the change via the next poll-and-push tick (within 50 ms) regardless, so even a failed send eventually propagates. 346/346 tests pass.

### H4 — `raw_proxy_loop` writes state on every packet [High / Concurrency] — **RESOLVED 2026-04-27**

**Location:** [src/console/ipad_connection.rs](../src/console/ipad_connection.rs) (`raw_proxy_loop`, `state_capture_loop`, `connect_mode3_proxy`).

**Status:** Resolved 2026-04-27. Mode 3's proxy hot path is now decoupled from state-mirror updates:

- `raw_proxy_loop` forwards bytes **first**, then `try_send`s a `ProxyCapture { bytes, direction }` into a bounded MPSC channel (capacity 256). The channel `try_send` never blocks — under backpressure (state-mirror task lagging behind), captures get dropped rather than slowing the byte path. Drops are counted and surfaced as a `warn!` at exponentially-spaced thresholds (1, 2, 4, 8, …) to avoid log spam.
- A dedicated `state_capture_loop` task drains the channel and runs the existing `log_and_capture_packet` (rosc-decode, iPad-parse, state-mirror update, dirty-tracker mark, snapshot-follow event). All state contention happens here, off the forwarding path.
- Cancellation token is shared between the two tasks: when the operator stops Mode 3, both exit cleanly (`raw_proxy_loop` drops `capture_tx`; `state_capture_loop` either gets cancelled or the channel closes via `Some(capture) => match`).

**Tradeoff:** state mirror can briefly fall behind reality during heavy traffic (capture drops on overload). Acceptable for a "best-effort observability" mirror — the next quiet period catches up, and proxy correctness (forwarding is faithful) is preserved. 346/346 tests pass; clippy clean.

### H5 — Trigger listener is unauthenticated [Medium / Security] — **DOWNGRADED & RESOLVED 2026-04-27**

**Location:** [src/osc/trigger_listener.rs](../src/osc/trigger_listener.rs), [src/model/cidr.rs](../src/model/cidr.rs), [src/persistence/show_file.rs](../src/persistence/show_file.rs).

**Status:** Downgraded from High to Medium 2026-04-27, then resolved with the same network-layer mitigation as C2:
- `TriggerListener::start_with_cancel` accepts an `allowlist: Vec<Ipv4Cidr>` (shared utility with the monitor server).
- `ConnectionSettings.trigger_allow_cidrs` field, CLI flag `--trigger-allow-cidr` (repeatable), show-file round-trip.
- Drops surface as `warn!` at exponentially-spaced thresholds.

**Observation:** `TriggerListener` accepts OSC packets from any source on its UDP port (default `53001`) and parses them into `TriggerEvent::FireCue / GoNext / GoPrevious / MacroFire / SnapshotRecall`. There is no allowlist of source IPs, no shared secret, no rate limit.

**Threat model:** the trigger port faces the FOH/show-control VLAN where QLab and the stage manager's laptop live. Misconfigured peers (wrong destination IP, stale show config) are the realistic concern, not an active attacker.

**Residual risk after mitigation:** a host on the operator's allowed subnet that's misconfigured can still fire cues. Acceptable — that's the same operator-trust surface as the GP OSC console connection itself.

**Recommendation (revised):**
1. **Bind trigger socket to a specific interface.** Same pattern as C2 recommendation #1; expose in the setup UI for the trigger port. Limits exposure to the show-control VLAN.
2. **Optional CIDR allowlist on the daemon.** `--trigger-allow-cidr` flag + setup-UI field. Drops packets from outside the range. Default: accept everything.
3. **Log `src` IP on every fired trigger** (cue / macro / snapshot recall). Currently only the *event* is logged, not the source. One-line addition.
4. The `/status/console` and `/status/clients` endpoints on the **monitor** server (not the trigger listener) should be in the same allowlist — they leak operational state to any querier, but the same closed-LAN reasoning applies.

**Effort:** S (1–2 h, can be done in the same UI/CLI pass as C2).

### H9 — Dead code: `IpadListener` / `IpadForwarder` [High / Code health] — **RESOLVED 2026-04-27**

**Location:** Was [src/osc/ipad_client.rs](../src/osc/ipad_client.rs) (lines 239–380 pre-deletion).

**Status:** Resolved 2026-04-27. Deleted the four dead items (`IpadListener`, `IpadForwarder`, `listener_receive_loop`, `process_packet_with_addr`) — ~143 LOC including doc comments. Verification: re-ran a grep across the repo to confirm no callers post-rebase, then deleted, then `cargo test` to surface any imports the grep missed. Build clean, 340/340 tests pass.

**Original observation:** `IpadListener`, `IpadForwarder`, `listener_receive_loop`, and `process_packet_with_addr` totaled ~143 lines. Grep across the entire src tree showed no users — the structs were defined but no module imported them outside their own file. **Original impact:**
