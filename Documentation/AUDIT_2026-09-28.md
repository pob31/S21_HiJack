# S21_HiJack Audit — 2026-09-28

## Executive summary

Since the [April audit](AUDIT_2026-04-27.md) the Rust daemon has grown from ~25.7k to ~75k LOC, adding a web monitor (axum + WebSocket), the Pad-protocol client, MIDI/D700 sidecar control, Stream Deck, MIDI triggers, backups/recovery, and two mobile clients. The toolchain hygiene the April audit asked for is in place and holding: **`cargo fmt --check` clean, `cargo clippy --all-targets -D warnings` clean, 828 tests passing (1 ignored)**.

The risks have moved from hygiene into three areas:

1. **Two ways to lose the show.** A single hostile/buggy UDP datagram aborts the whole process (stack overflow in the OSC bundle decoder — reproduced), and a save onto a full disk reports success while replacing the good show with a truncated one (tokio swallows the write error — confirmed from tokio's source).
2. **Lifecycle and lock-order bugs in the newer wiring.** The Mode 2 iPad link is never torn down on Disconnect (found independently by three reviewers), there are two lock-order cycles that can freeze UI + inbound + save together, and `New`/`Open` leave stale indexes and half of the previous show behind.
3. **Non-finite floats.** Nothing in the codebase checks `is_finite`. NaN/inf from the network or a text field can panic a recall, wedge dirty-suppression permanently, go to the console raw, and — because serde_json writes NaN as `null` — make the saved show file unloadable.

4. **The Android monitor app can put the wrong level in a musician's ears.** After switching aux, faders still drive the previous aux (and a daemon echo quirk can shift every strip onto its neighbour's input), and a fader jumps to wherever the finger lands. See [A1/A2](#android-monitor-app-monitor_android).

Plus one plain correctness bug with show impact: **outbound GP OSC always assumes 8 auxes**, so on any other aux/group split, writes to Group channels land on the wrong bus.

### Methodology

- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`, `cargo audit` on rustc 1.94.1 (Linux).
- Seven parallel deep reviews by subsystem (network servers; console pipeline & concurrency; iPad/Pad protocol & parsers; hardware sidecar/Stream Deck/MIDI; persistence/model/platform; egui UI; mobile apps/packaging/CI). Every Critical and most High findings were then re-verified by reading the cited code directly; the two Criticals were reproduced/confirmed against dependency source.
- Static analysis plus small out-of-tree repro programs only. No hardware, no device testing of the mobile apps.
- Threat model unchanged from April: closed show LAN, operator-controlled devices. Findings that only matter on a hostile network are rated accordingly; findings a *misbehaving* peer or a typo can trigger are not discounted.

## Critical

### C1 — Nested OSC bundle aborts the process — **RESOLVED 2026-09-28**

**Status:** Resolved. `decode_udp_tolerant` and the monitor and trigger listeners now go through `decode_udp_bounded` ([src/osc/mod.rs](../src/osc/mod.rs)), which walks the datagram's bundle and array structure without recursing and refuses anything nested deeper than 8 levels. Array nesting turned out to be a second route to the same abort. rosc reads `[` tags iteratively, but the value it builds nests one level per bracket and is dropped recursively, so ~30,000 brackets in one datagram overflow the stack too. Both were reproduced in a release build before the fix. Proptests check the guard against rosc itself: nothing decoded exceeds the limit, even from truncated or corrupted bytes, and well-formed packets within the limit round-trip unchanged.

**Where:** [src/osc/mod.rs:37](../src/osc/mod.rs#L37) `decode_udp_tolerant` → `rosc 0.10.1` `decoder.rs` (`decode_packet` ↔ `decode_bundle` recurse with no depth limit). Reached from 64 KiB receive buffers at [src/osc/client.rs:226](../src/osc/client.rs#L226) (GP), [src/osc/ipad_client.rs:163](../src/osc/ipad_client.rs#L163) (Mode 2 / Pad), [src/console/ipad_connection.rs:356](../src/console/ipad_connection.rs#L356) (Mode 3 iPad listen port).

**What:** Each nesting level costs 20 bytes, so ~2,800 levels fit in a 56 KB datagram. Reproduced out-of-tree against rosc 0.10.1 on a 2 MiB stack (tokio's default worker stack): `thread has overflowed its stack — fatal runtime error: stack overflow, aborting`. Debug builds die at ~1,000 levels. A stack overflow is an abort, not a panic — nothing catches it.

**Scenario:** Any host on the LAN sends one datagram to the Mode 3 iPad port (not source-filtered) or the GP/Mode 2 local port (GP ignores the sender — see M9). The daemon and UI vanish mid-show.

**Not affected:** monitor server and trigger listener use 4 KiB buffers (≤ ~200 levels — safe).

**Fix:** Before calling rosc, walk bundle headers iteratively and reject datagrams nested deeper than ~8 (DiGiCo never nests). Add a bundle-aware proptest strategy for `decode_udp_tolerant`.

### C2 — Failed save reported as success — **RESOLVED 2026-09-28**

**Status:** Resolved. Show saves and backup copies now share one `write_atomically` ([src/persistence/atomic_write.rs](../src/persistence/atomic_write.rs)), which does the write, fsync and rename on a blocking thread with `std::fs`, so any write error is returned as-is. That replaces the two `tokio::fs` copies rather than adding `flush()` to each, so a future write path can't miss it. A Linux-only test writes to `/dev/full` to cover the full-disk case. The Low "Save durability" items (fixed `.tmp` name, no parent-directory fsync, symlink replacement) are unchanged.

**Where:** [src/persistence/show_file.rs:306-311](../src/persistence/show_file.rs#L306-L311); same pattern in [src/persistence/backup.rs:203-207](../src/persistence/backup.rs#L203-L207).

**What:** `tokio::fs::File::write_all` hands the final buffer to a blocking task and returns `Ok` immediately. `sync_all()` then calls `complete_inflight()`, which on error only stores `last_write_err` and returns `()` (tokio 1.52.3 `fs/file.rs:317-322, 1079-1088`); the fsync itself succeeds. The error is dropped with the file handle. A reviewer confirmed it end to end under `ulimit -f`: the write failed at 20 KB and `write_all` + `sync_all` both returned `Ok`.

**Scenario:** A disk is full (e.g. a Pi SD card filled by logs, see M13). The operator hits Save; a truncated `.tmp` is renamed over the good show and the UI says "Saved". Autosaves then rotate out the good backups with equally truncated copies.

**Fix:** `file.flush().await?;` before `file.sync_all().await?` in both places (verified to surface the error). Or do the whole write+fsync+rename inside one `spawn_blocking` with `std::fs`.

## High

### H1 — GP OSC bus numbering is asymmetric — **RESOLVED 2026-09-28**

**Status:** Resolved.
- **Encoding.** `ChannelId::to_gp_osc_number_with_config` is the exact inverse of the config-aware parser, with per-type range checks (Input 1–60, CG 1–10, Matrix 1–8, Aux/Group by the layout, or 8/16 before one is known). Proptests check both directions under random layouts. "CG 11" no longer encodes as Matrix 1.
- **Send path.** Every clone of the GP `OscSender` shares a `GpBusLayout`. The GP state-mirror loop publishes `mix_output_types` to it at start-up, when the counts arrive and on every 1 s tick (which picks up a layout reported over the iPad link), and `ConsoleTx` encodes with it. The QLab per-parameter export uses the live layout too.
- **Related items.** `apply_channel_counts` now replaces a layout that disagrees with the counts (it keeps one with the right number of auxes, such as an interleaved layout from the iPad handshake). Only `/Console/Aux_Outputs/types` sets the layout.
- **Mock console.** It laid groups out from bus 78 whatever `--auxes` said and only sent per-type counts. It now places groups straight after the auxes, replies with the positional counts the S21+ uses, and logs each write by the channel it lands on, so `--auxes 10 --groups 14` exercises a non-default split.

**Where:** encode [src/model/channel.rs:36-41](../src/model/channel.rs#L36-L41) (Aux n → 69+n, Group n → 77+n, always); parse [src/model/channel.rs:59-83](../src/model/channel.rs#L59-L83) (counts through `mix_output_types`). Used by [src/osc/encode.rs:52,63](../src/osc/encode.rs#L52).

**What:** The desk's 24-bus pool is split between auxes and groups by configuration. Inbound parsing honours the split; outbound always assumes 8 aux. On a 10-aux/14-group desk, inbound bus 78 is Aux 9 but outbound `Group(1)` is also sent to 78. On a 6-aux desk, Group 1 is really bus 76.

**Consequence:** Recalls, gangs and macros that target Group channels (or Aux 9+) write the wrong bus. Related:
- `mix_output_types` is only regenerated when empty ([src/console/discovery.rs:30](../src/console/discovery.rs#L30)), so it goes stale after a desk reconfiguration or when it's restored from an old show file.
- Any path ending in `/types` replaces it ([src/osc/ipad_parse.rs:196](../src/osc/ipad_parse.rs#L196)).
- A free-text "CG 11" macro target encodes to 120, which is Matrix 1.

**Fix:** Add a config-aware `to_gp_osc_number_with_config` (the inverse of the parser) with per-type range checks, and use it on the send path. Add a proptest round trip under non-default `mix_output_types`.

### H2 — Mode 2 iPad link is never shut down — **RESOLVED 2026-09-28**

**Status:** Resolved. `connect_mode2` now takes the connection's cancel token (UI and headless). It splits the client with `into_parts_with_cancel`, so the receive loop stops and releases its socket, and `ipad_state_mirror_loop` selects on the token, so Disconnect ends it even while packets are still arriving. The receive loop also stops when its channel closes. The unused `JoinHandle` return is gone. M1 (a macro's [Disconnect, Connect] clearing the new token) is a separate race and is still open.

**Where:** [src/console/ipad_connection.rs:67](../src/console/ipad_connection.rs#L67) uses `client.into_parts()` (a fresh, never-cancelled token); the mirror task at `:88` has no cancel; the UI drops the handle ([src/ui/setup_tab.rs:2449](../src/ui/setup_tab.rs#L2449)). `receive_loop` doesn't exit when its channel closes ([src/osc/ipad_client.rs:191](../src/osc/ipad_client.rs#L191)).

**Scenario:** After Disconnect, the old socket and mirror loop keep writing the shared state and dirty tracker. They also keep running gang and pan-link propagation to the desk through the old senders, and keep `snap_event_tx` alive, so follow mode can still fire recalls. Every reconnect adds another set, so propagation doubles each time. A fixed local port on reconnect gets EADDRINUSE (macOS) or split delivery (Linux).

**Fix:** Pass the connection token into `connect_mode2`, use `into_parts_with_cancel(token)`, and `select!` on it in `ipad_state_mirror_loop`.

### H3 — Non-finite floats are accepted everywhere — **RESOLVED 2026-09-28**

**Status:** Resolved.
- **Network input.** The GP and iPad parsers drop NaN and ±inf, including a double that only becomes infinite when narrowed to f32 (`1e39`), and no longer turn a NaN into an int, bool or meter index. Inline `nan`/`inf` in DiGiCo bare packets stay strings. The monitor engine refuses non-finite values from phones and browsers before its optimistic mirror write, and `/cue/fire` refuses a non-finite cue number.
- **UI text fields.** Timings, cue numbers, macro values (fixed and relative) and cue-trigger OSC args parse through `parse_finite_f32`. The Probe tab is deliberately unchanged: it is a raw protocol tool and never writes the mirror.
- **Outbound backstop.** `ConsoleTx` refuses any non-finite value (`SendOutcome::NonFinite`), so nothing can send `inf` to the desk whatever produced it.
- **Recall.** Timings convert through `Duration::try_from_secs_f32` (`CategoryTiming::pre_wait()`/`fade_time()`, `secs_to_duration`), so an unusable value reads as zero instead of panicking. Dirty suppression is now an RAII `SuppressionGuard` (`DirtyTracker::suppress`), so a panic or a cancelled recall still ends it.
- **Show load.** Timings are clamped to 0–30 s on load, and `null` (a NaN as serde_json writes it) reads as 0, so a show saved with a NaN timing loads again. Other float fields can't be recovered that way without guessing a value (0 dB is unity on a fader), so they rely on NaN never getting in.
- `normalized_to_db(NaN)` now returns −150 dB instead of +10 dB. Cues sort with `total_cmp`.

**Where:**
- Network input: [src/osc/parse.rs:171](../src/osc/parse.rs#L171) `extract_float`; [src/osc/ipad_parse.rs:403](../src/osc/ipad_parse.rs#L403); inline `"nan"`/`"inf"` at [src/osc/ipad_client.rs:243](../src/osc/ipad_client.rs#L243); [src/web/protocol.rs](../src/web/protocol.rs) (serde parses `1e39` to `inf`); the UDP monitor server.
- UI text fields: `parse_timing_secs` at [src/ui/scope_editor/state.rs:533](../src/ui/scope_editor/state.rs#L533) (`clamp` passes NaN through), cue numbers, macro values, trigger args. Rust's float parser accepts "nan"/"inf" in any case.

**Consequences:**
- **Panic in a recall.** `Duration::from_secs_f32(NaN)` panics at [src/console/snapshot_engine.rs:1585](../src/console/snapshot_engine.rs#L1585) (also `:1587, 1600, 1937, 2029`). That happens inside `with_dirty_suppression` (`:667-681`), which is not panic-safe, so the suppression depth never comes back down. That permanently disables pan link, the palette absorb loop and autosave.
- **Unloadable show file.** serde_json writes NaN as `null` and refuses to read it back as `f32`, so the show and every later autosave fail to load and are classed as corrupt.
- **Raw values to the desk.** `inf`/`NaN` are sent to the console as-is (`/channel/70/fader inf`). A NaN in the mirror also defeats the monitor poll's `old == new` check, so the value is re-pushed forever.
- **Wrong value on `/sd`.** `normalized_to_db(NaN)` returns +10 dB.

**Fix:**
- Drop non-finite values in every `extract_*` and parse helper, and in every UI parse helper (`.filter(|v| v.is_finite())`).
- Clamp timings on show load.
- Use `Duration::try_from_secs_f32`.
- Make dirty suppression an RAII guard.

### H4 — Lock-order cycles can deadlock UI, inbound and save — **RESOLVED 2026-09-28**

**Status:** Resolved. None of these paths holds two of these locks at once any more.
- **(a) Gangs.** Inbound copies the gangs containing the moved channel (`GangManager::snapshot_for_channel`) and releases the manager before propagating. Pan link copies its gang lists before taking `state`.
- **(b) Stream Deck.** The resize helper, the button-press refresh and the step-list edits (now one `edit_button_and_refresh`) release the config before reading the macro manager.
- **Save.** `build_show_file` copies from each lock and releases it before taking the next.
- **Inbound learn.** Inbound checks macro learn under a read lock and only takes the write lock while recording, instead of queuing a write on every message.
- **Test.** A regression test parks a gang propagation on the state lock and checks that a gang edit still gets the manager's write lock. It fails with the old code.
- **April H2.** The gang *manager* lock is no longer held across sends. The gang *engine* lock still is, but only the inbound paths take it and they never hold another lock while waiting for it.

tokio's `RwLock` is fair: a queued writer blocks new readers. Two cycles:

- **(a) Gangs.** The inbound path holds `gang_manager.read()` ([src/console/inbound.rs:176-180](../src/console/inbound.rs#L176-L180)) while `process_gang_update` takes `state.read/write` ([src/console/gang_engine.rs:202,252,341](../src/console/gang_engine.rs#L202)). `build_show_file` ([src/ui/setup_tab.rs:3186-3194](../src/ui/setup_tab.rs#L3186-L3194), used by autosave and Save) holds `state.read()` and then takes eight more reads including `gang_manager`. Pan link also takes `state` then `gang_manager`. Scenario: a gang fan-out is running during autosave while the operator toggles a gang (a queued `gang_manager.write()`). Nothing can make progress.
- **(b) Stream Deck.** `streamdeck_resize_and_collect_labels` ([src/ui/app.rs:1754-1780](../src/ui/app.rs#L1754-L1780), on the UI thread) holds `stream_deck_config.write()` while waiting for `macro_manager.read()`. `build_show_file` holds `macro_manager.read` while waiting for `stream_deck_config.read`. Inbound takes `macro_manager.write()` on every change.

**Fix:** In `build_show_file`, clone each manager and drop its guard before taking the next. In inbound, clone the matching gangs and drop `gang_manager` before propagating. Never `block_on` a lock from the UI while holding another. This also covers April's **H2** (gang lock held across sends), which is still open.

### H5 — UI panic on stale cue index — **RESOLVED 2026-09-28**

**Status:** Resolved. New and Open go through `CueManager::replace_cue_list`, which resets the playhead and the last-recalled snapshot. `current_cue()` uses `.get()`, and `go_previous()` clamps a playhead left past the end, so even a list swapped by direct field access can't index out of bounds.

**Where:** `current_cue()` indexes `cues[i]` unchecked at [src/console/cue_manager.rs:212](../src/console/cue_manager.rs#L212). New Show ([src/ui/setup_tab.rs:1554](../src/ui/setup_tab.rs#L1554)) and show load (`:3267`) replace `cue_list` without resetting `current_cue_index`. [src/ui/snapshots_tab.rs:241](../src/ui/snapshots_tab.rs#L241) calls it every frame.

**Scenario:** The operator is on cue 12 and chooses New (or opens a show with fewer cues). The app crashes on the next frame.

**Fix:** Use `.get(i)`, and add a `replace_cue_list()` that also resets the index and `last_recalled`.

### H6 — Headless mode ignores the show file — **RESOLVED 2026-09-28**

**Status:** Resolved. `run_headless` loads the show before anything connects.
- **What loads.** Cues, snapshots, scope templates, OSC targets, trigger templates, macros, palettes, monitor clients, gangs, pan link and the console config all come from the show. The recall behaviour it was saved with (sync direction, auto-update on recall) is applied, and the snapshot engine now has the cue manager, as in the UI.
- **Failures.** A file that fails to load stops the daemon with the reason. Starting without a file logs a warning that cue and snapshot triggers will do nothing.
- **Not taken from the show.** Network settings stay with the command line. Stream Deck and sidecar configs aren't used, because headless doesn't run those devices.
- **Live check.** The headless daemon was run against the mock console set to 10 aux / 14 group, with a show whose macro writes Group 1, Aux 9, Group 14 and CG 11. The mock received the first three on the right buses (which also confirms H1), and CG 11 was refused.

**Where:** [src/main.rs:198-290](../src/main.rs#L198-L290). `args.show_file` is only passed to `run_ui` (`:669`).

**Scenario:** The README describes the headless Pi as a primary deployment. There, cue, macro, palette and gang managers start empty, so `/cue/go` and `/snapshot/recall` do nothing, with no warning.

**Fix:** Load `args.show_file` in `run_headless` and populate the managers and config (and warn loudly if none was given).

### H7 — Sidecar moves bypass the "operator change" pipeline — **RESOLVED 2026-09-28**

**Status:** Resolved.
- **The fix.** After a successful send, the sidecar runs `inbound::apply_operator_change`: the same chain as a move on the desk, without the echo check (the send has just put the value in the sent-value log, so that check would always call it an echo). So a D700 or MIDI move now cancels a running fade on that parameter, propagates through gangs and pan link, marks the cell dirty and is recorded by macro learn. The chain also updates the mirror, replacing the sidecar's own optimistic update.
- **Wiring.** The service now receives a `SidecarLink` (write path plus the connection's `DaemonState`) instead of a bare `ConsoleTx`. The service's header comment and `Documentation/sidecar.md` no longer claim the console echo does this. The doc's test step 4 now says to move the fader, since touching it sends nothing.
- **Test.** A new test checks that a sidecar move drags a relative gang sibling and marks the fader dirty. The M19–M22 sidecar and Stream Deck items are separate and still open.

**Where:** [src/console/sidecar_service.rs:316-329](../src/console/sidecar_service.rs#L316-L329). The header comment at `:33-36` claims the console echo drives `maybe_override`. It can't: GP doesn't echo, and the iPad echo is marked as our own by `sent_log.is_echo` and skipped ([src/console/inbound.rs:129-186](../src/console/inbound.rs#L129-L186)). The optimistic mirror update also makes `old == new`.

**Consequence:** D700 or MIDI moves never cancel a running fade (the operator fights the automation), never propagate through gangs or pan link, never mark the channel dirty, and never get recorded in macro learn. `Documentation/sidecar.md` test step 4 cannot pass.

**Fix:** Route hardware-originated sends through the same operator-change routine inbound uses: override registry, gang, pan link, dirty tracker.

### H8 — Unsaved edits lost without a prompt — **RESOLVED 2026-09-28**

**Status:** Resolved.
- **Detecting changes.** `ShowFile::edit_fingerprint` hashes the show content the operator edits. It leaves out the console config (rewritten by the desk on every connect), the connection settings, the version fields and the Stream Deck cursors and padding, and sorts collections by id so manager hash order can't matter. The app keeps the fingerprint of the show as last saved, loaded or created, and the show has unsaved changes when the current one differs.
- **Prompts.** Close, Open and New now check for unsaved changes first and raise a modal with Save (Save As… for an untitled show), continue without saving, or Cancel. Save runs on the spot and the action continues once it has landed. A failed save is shown in the modal. The "quit while connected" modal still covers the case where nothing is unsaved. If the show can't be read within 2 s, the check assumes there are changes and asks.
- **Untitled shows.** They are autosaved on the same schedule to `<config dir>/s21_hijack/untitled/.s21backups/`, and the prompt says so. An untouched untitled show isn't written.
- **Exit.** `on_exit` waits up to 10 s for running saves and the latest autosave before the runtime is dropped.
- **Not exercised by hand.** The modals haven't been tried in the running app. Tests cover the fingerprint: it ignores the excluded fields and manager order, and changes on a real edit, both on `ShowFile` directly and through `build_show_file`.

**Where:** No show-level dirty flag exists. Closing the window while disconnected quits immediately ([src/ui/app.rs:2346-2354](../src/ui/app.rs#L2346-L2354)); Open and New replace the show without asking; untitled shows are never autosaved ([src/ui/app.rs:1788](../src/ui/app.rs#L1788)). Dropping the runtime on exit ([src/main.rs:699](../src/main.rs#L699)) also cancels an in-flight save.

**Scenario:** After hours of offline cue building in an untitled show, closing the window loses everything.

**Fix:** Keep a show-dirty generation, prompt on close, Open and New, autosave untitled shows to a scratch folder, and await any in-flight save before exit.

### H9 — Web monitor access control — **ACCEPTED 2026-09-28**

**Status:** Accepted by operator decision. Open access to the HTML monitor is intentional; the deployment relies on network security. The observations are kept below for the record. M17 (WebSocket sessions outliving shutdown) is a lifecycle bug rather than access control, so it stays open.

**Where:** [src/web/mod.rs](../src/web/mod.rs), [src/ui/setup_tab.rs:2773](../src/ui/setup_tab.rs#L2773), [src/main.rs:545](../src/main.rs#L545).

The web monitor is new since April and on by default. It has several gaps that stack:
- **No Origin check on the WebSocket upgrade (`mod.rs:123`).** Any web page opened on a musician's phone on the show Wi-Fi can open `ws://<daemon>:8080/ws`, send `hello` with a profile name, and take over that mix. That page can also brute-force PINs, because failed attempts aren't rate-limited.
- **Binds `0.0.0.0` regardless of the interface selection.** Unlike the UDP listeners, it ignores the selected interface, so a dual-homed laptop serves mix control on the venue Wi-Fi too.
- **tungstenite defaults.** Messages up to 64 MiB, no `Hello` timeout, no idle timeout and no connection cap mean a few peers can push the daemon to OOM or exhaust file descriptors.
- **PIN is advisory while UDP is open.** It is documented as web-only ([src/model/monitor.rs:31-34](../src/model/monitor.rs#L31-L34)), but the UDP monitor path (port 8025, on by default) accepts the same profile name with no PIN. It rebinds the endpoint and returns full mix state.

**Fix:**
- Check `Origin` against `Host` (or an allowlist).
- `ws.max_message_size(4096)`, a `Hello` timeout, a connection cap, and a per-IP backoff after failed PINs.
- Bind the web server to the selected interface.
- Either refuse UDP commands for PIN-protected profiles or document plainly that a PIN only works with UDP monitoring disabled.

### A1 — Faders and pan control the wrong aux or input [Critical] — **RESOLVED 2026-09-28**

**Status:** Resolved.

- The app ignores echoes for sends it doesn't already have (`MonitorUiState.withSendEcho`).

Unit tests cover the app's echo rule and the daemon's echo recipients; the daemon tests fail with the old code. The Compose changes build and pass lint, but haven't been tried on a phone.

**Where:** `pointerInput(Unit)` in [ui/widgets/Faders.kt:76-84, 131-142](../monitor_android/app/src/main/java/com/pob31/s21monitor/ui/widgets/Faders.kt#L76-L84) keeps the `onDb`/`onPan` lambda from the first composition. Strips are rendered with a plain `forEach` and no `key()` ([ui/MonitorScreen.kt:236-243, 257-264](../monitor_android/app/src/main/java/com/pob31/s21monitor/ui/MonitorScreen.kt#L236-L243)), so Compose reuses them by position. The ON/MUTE buttons use `clickable`, which does pick up new lambdas, so they route correctly while the fader in the same strip doesn't.

**Scenario A — aux switch:** The drummer has aux 3 (IEMs) and aux 4 (sidefill). He selects aux 4 and pushes Kick up. The packet goes to aux 3, so his in-ears get louder, and the on-screen aux 4 fader doesn't move, so he pushes harder.

**Scenario B — ghost strip:** The daemon echoes other clients' moves without checking `visible_inputs`, deliberately ([src/console/monitor_event.rs:187-188](../src/console/monitor_event.rs#L187-L188)). The app then creates a strip for an input this musician can't see, and `sendsForAux` sorts it into the middle of the row ([model/MonitorState.kt:41-42](../monitor_android/app/src/main/java/com/pob31/s21monitor/model/MonitorState.kt#L41-L42)). Every strip after it now controls its neighbour's input. A late full snapshot, or a `visible_inputs` list that isn't in ascending order, can shift the row in the same way.

**Fix:**
- Wrap each strip in `key(send.input, send.aux)` (and the aux-master strips in `key(aux)`).
- Use `rememberUpdatedState(onDb)` / `rememberUpdatedState(onPan)` inside the gesture, or key `pointerInput` on `(input, aux)`.
- In the app, ignore echoes for sends it doesn't already know.
- On the daemon, apply the `visible_inputs` check on the echo path too.

### A2 — A fader jumps to wherever the finger lands [Critical] — **RESOLVED 2026-09-28**

**Status:** Resolved. Fader drags are relative (`dragDb` in `ui/widgets/Faders.kt`): the level when the drag began plus the finger's travel, with the fader's full height spanning the full range, as in the web client.
- Nothing is sent until the level moves, so a downward drag on a fader that's off no longer sends the −80 dB floor.
- A drag starts only if the finger passes the touch slop vertically before the row's scroller sees as much horizontal travel. That is the web client's 45° direction lock.
- The start level is fixed when the drag begins, so incoming state during a drag (A5) can't change the level being sent. The display jitter it still caused is fixed by A5.
- The pan control still jumps to the touch point, as the web client's pan slider does.

Unit tests cover the drag arithmetic. Not tried on a phone.

**Where:** `onDragStart = { setFromY(it.y) }` in [ui/widgets/Faders.kt:78](../monitor_android/app/src/main/java/com/pob31/s21monitor/ui/widgets/Faders.kt#L78). Fader position is absolute. The web client (relative drag with a direction lock) and the Flutter client (grab offset) both avoid this; the comment saying the range "matches the web/Flutter clients" is misleading.

**Scenario:** A vocal send is at −30 dB. The musician puts a thumb near the top of the fader to nudge it, and the send goes to about +8 dB instantly. A steep diagonal swipe meant to scroll the strip row can do the same.

**Fix:** Anchor on the current value, apply only the drag delta, and lock the drag direction the way the web client does.

### A3 — Sends can arrive out of order; the final value isn't guaranteed [High] — **RESOLVED 2026-09-28**

**Status:** Resolved. `MonitorService` puts outbound packets in an `OutboundQueue` ([service/OutboundQueue.kt](../monitor_android/app/src/main/java/com/pob31/s21monitor/service/OutboundQueue.kt)), which one sender coroutine drains, so they leave in the order they were queued.
- A newer value for an OSC address replaces one still waiting, so a fast drag sends its latest value rather than a backlog.
- Every control value (send level, pan and ON; aux fader and mute) is sent once more after it has been still for 250 ms, so a lost final packet no longer leaves the desk on an older value.
- The daemon's address is resolved once per link, not per packet.

Unit tests cover the queue. Not tried on a phone.

**Where:** [service/MonitorService.kt:260-272](../monitor_android/app/src/main/java/com/pob31/s21monitor/service/MonitorService.kt#L260-L272). Each packet gets its own `scope.launch` on `Dispatchers.IO` plus an `InetAddress.getByName` lookup. Nothing orders or coalesces them, and nothing is resent on release.

**Scenario:** A musician pulls a channel down fast to kill it. The −60 dB packet is sent after the −80 dB one, or the last UDP packet is lost. The desk stays at −60 while the phone shows "-inf" (see A6), until the next full snapshot up to 10 s later.

**Fix:** Use one sender coroutine reading a conflated channel keyed by OSC path, resolve the host once per connection, and resend the final value when the drag ends.

### A4 — The Android 15+ foreground-service time limit isn't handled [High] — **RESOLVED 2026-09-28**

**Status:** Resolved. The service is now a `connectedDevice` foreground service (it controls the desk over the network), and that type has no daily time limit. The manifest declares `FOREGROUND_SERVICE_CONNECTED_DEVICE`, plus `CHANGE_NETWORK_STATE`, one of the permissions Android 14+ requires for this type.
- `goForeground()` catches a refused start (`ForegroundServiceStartNotAllowedException` on a sticky restart in the background, or a `SecurityException`) and stops the service instead of crashing. Opening the app starts it again.
- `onTimeout` is handled as a safety net: it ends the link, stops the service and leaves a notification saying to reopen the app.
- Disconnect and service stop now end the link in one place (`stopLink`): its coroutines, receive thread, socket and queue.

Builds and passes lint. Not tried on a device, so neither a long run nor a sticky restart has been exercised.

**Where:** `MonitorService` has no `onTimeout`, and the service type is `dataSync` ([AndroidManifest.xml:36-37](../monitor_android/app/src/main/AndroidManifest.xml#L36-L37)). With targetSdk 36, Android caps `dataSync` services at about 6 hours per 24 hours. The system then calls `onTimeout`. If the service doesn't stop, the app crashes with `ForegroundServiceDidNotStopInTimeException`, and later `startForeground` calls throw in `goForeground()`, which has no try/catch.

**Scenario:** On a long rehearsal-plus-show day with the phone locked, the service dies mid-show, and relaunching the app may crash too.

**Fix:** Override `onTimeout` to stop cleanly and tell the user, catch `ForegroundServiceStartNotAllowedException`, or move to a `specialUse` or `connectedDevice` service type that has no time limit.
