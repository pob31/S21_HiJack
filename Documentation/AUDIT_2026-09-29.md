## Priority 1 — safety

### R0 — A relative drag can start from a false 0 dB (High)

**Problem:** When the daemon hasn't mirrored a send's level from the desk yet, it reports it as 0 dB (unity) instead of off. Since the A2 fix, phone faders drag *relative to the displayed value*. Scenario: a send is at −inf on the desk, but the phone shows 0 dB. The musician nudges it down 2 mm, and the desk jumps from −inf to about −3 dB in their ears. The web client has the same fallback.

**Where:**
- Daemon, per-send level fallback `unwrap_or(0.0)`:
  - [src/console/monitor_engine.rs:391](../src/console/monitor_engine.rs#L391) (snapshot)
  - [:569](../src/console/monitor_engine.rs#L569) (20 Hz poll)
  - Aux masters already use `FADER_INF_DB` (`:442`, `:630`); make sends match.
- Web client: `S.sends.get(k) || { level: 0, pan: 0, on: false }` at [web/dist/index.html:295, 300, 350, 383](../web/dist/index.html#L295).

**Fix:**
- Daemon: use `unwrap_or(FADER_INF_DB)` for send levels. Pan's 0 (centre) fallback is fine.
- Web client: use a level of −150 (the daemon's off value) in those four fallbacks.
- Optional hardening: have the phone and web client refuse to start a relative drag on a send they have never received a value for.

**Verify:** a daemon unit test in which a profile with an unmirrored send gets `FADER_INF_DB` for it in the snapshot and in the poll.

**Status: fixed.** Both daemon sites fall back to `FADER_INF_DB`. The web client uses `OFF_DB = -150` for all four send fallbacks and for its two aux-master fallbacks, which also said 0. The Android app already defaulted unknown sends to off, so the daemon was its only source of a false 0 dB. The optional "refuse to drag a never-received send" hardening wasn't needed: every visible send now arrives in the snapshot with a real or off value. Test: `monitor_engine::tests::unmirrored_sends_read_as_off`.

## Priority 2 — small robustness fixes

### R1 — The WebSocket shutdown fix can panic (Medium)

**Where:** [src/web/mod.rs:271-307](../src/web/mod.rs#L271-L307).

**Problem:** The read loop's `tokio::select!` isn't `biased`. When the write task finishes after sending the Close frame, the loop can take the `_ = &mut write => break` branch, which consumes the finished `JoinHandle`. Because `shutdown.is_cancelled()` is true, the loop then calls `timeout(1s, &mut write)` and polls the handle again. tokio panics with "JoinHandle polled after completion"; this was reproduced standalone with tokio 1.52.3. Roughly half of browser sessions panic on each Disconnect, and every panic writes a backtrace to `crashes.log`.

**Fix:** record whether the write branch already fired (`let mut write_done = false;` set in that arm) and skip the timeout if so. Checking `!write.is_finished()` first, or using `biased;` with shutdown first, also works.

**Verify:** extend the existing shutdown test to run the disconnect many times, or force the write task to finish first. It must not panic.

**Status: fixed.** Teardown moved to `stop_write_task`, which skips the grace wait when the task `is_finished()` (a handle can only have been polled to completion once its task has finished). An end-to-end loop didn't reproduce the race: on the test's single-threaded runtime the read loop always wakes first. So the test forces the order, polling the handle to completion first, as the `select!` arm does. It hits tokio's "JoinHandle polled after completion" without the fix. Test: `web::tests::stopping_a_finished_write_task_does_not_panic`.

### R6 — A failed Pad-only connect is never shown (Medium)

**Where:** [src/ui/setup_tab.rs:3106-3111](../src/ui/setup_tab.rs#L3106-L3111), and the filter at [src/ui/app.rs:1147-1149](../src/ui/app.rs#L1147-L1149).

**Problem:** On failure the task calls `token.cancel()` and then sends `ConnectionFailed { token }`. The UI drops any event whose token is cancelled, so the status stays at "Connecting…" with no reason given.

**Also in this path:**
- The success path raises `conn_flag` without checking whether the connection was cancelled (`:3091-3092`).
- The failure path clears `conn_flag` even when a newer connection owns it (`:3108`).

This is the remainder of M2.

**Fix:**
- Send `ConnectionFailed` before calling `cancel()`, or give the event a flag the UI filter respects.
- Check `token.is_cancelled()` before raising the flag.
- Only clear the flag if this token is still the live one, mirroring what the GP path now does.

**Status: fixed.** Sending the event before `cancel()` isn't enough, because the UI checks the token when it drains the event, which is after the cancel. Instead, the Pad link's loops now run on a child of the connection's token. A failed handshake cancels only the child, which frees the port, so the connection's token stays live and the UI shows "Connection failed: …". Disconnect cancels the parent, and with it the child. The task no longer clears `conn_flag` itself: the UI's `ConnectionFailed` handler already does so only for a live token. The flag is raised only if the token isn't cancelled, as on the GP path. No automated test, since this path needs the full UI to drive.

### R7 — The monitor server and trigger listener still stop on any receive error (Medium)

**Where:** [src/osc/monitor_server.rs:236](../src/osc/monitor_server.rs#L236) and [src/osc/trigger_listener.rs:119](../src/osc/trigger_listener.rs#L119). Both `break` on any `recv_from` error.

**Problem:** On Windows, an ICMP port-unreachable reply to an earlier send arrives as `WSAECONNRESET` on the next receive. So one phone or QLab machine going away can silently stop all monitor control or all cue triggers until the operator reconnects. The M9 fix applied a "carry on" rule to the GP and iPad loops only.

**Fix:** reuse the M9 rule from [src/osc/client.rs](../src/osc/client.rs) (`recv_error_pause`/`ConnectionReset` handling): continue straight away on a connection reset, and after a short pause on other errors. Throttle the log line; see the Lows.

**Status: fixed.** Both loops use `recv_error_pause`, which already throttles its log line (since `03dd4d0`). A second trigger on Windows kills these loops just as surely: a datagram larger than the 4 KB buffer is a `WSAEMSGSIZE` error from `recv_from`. The trigger listener's socket never sends, so it can't get the ICMP reset itself, but it did die on an oversized packet. Tests: `monitor_server::tests::receive_errors_do_not_stop_the_server` (an oversized packet, plus a reply to a vanished client) and `trigger_listener::tests::receive_errors_do_not_stop_the_listener`. Both fail on the old `break`.

### Pad health drops from Lost back to Stale (Low, but in the same area)

**Where:** [src/console/pad_connection.rs:374-393](../src/console/pad_connection.rs#L374-L393).

**Problem:** When the enumeration sweep ends, the heartbeat branch starts counting misses from 0. A desk already marked Lost is shown as Stale for about 6 s before going Lost again.

**Fix:** when the sweep ends, seed `misses` from `last_inbound.elapsed() / HEARTBEAT_INTERVAL`, or never step health down from Lost without inbound traffic.

**Status: fixed.** Each missed beat now counts as `max(misses + 1, beats of silence)` (`count_missed_beat`), so silence from the sweep carries over. The sweep's own check shares the same `silent_beats` helper. Test: `pad_connection::tests::silence_from_the_sweep_counts_as_missed_beats`. The existing 15 s heartbeat timing test still passes.

## Priority 3 — show data

### R4 — Changed connection and recall settings aren't treated as unsaved edits (Medium)

**Where:** `ShowFile::edit_fingerprint` in [src/persistence/show_file.rs](../src/persistence/show_file.rs). The test near `:528` asserts that changing `console_ip` is *not* an edit.

**Problem:** The fingerprint leaves out `ConnectionSettings` on the grounds that they are "kept in preferences". `AppPreferences` ([src/persistence/preferences.rs:57-117](../src/persistence/preferences.rs#L57-L117)) stores none of them: not the IPs, ports, operating mode, allowlists or QLab settings, and not the sync direction or auto-update-on-recall. If the operator changes any of these offline and quits, the changes are lost without a prompt.

**Fix:**
- Include every show-owned connection field in the fingerprint, i.e. all except `send_pace_us` and `ui_mode`, which really are preferences.
- Update the test so that a console IP or sync-direction change *does* count as an edit.

**Status: fixed.** `edit_fingerprint` now covers the connection settings, with `send_pace_us` and `ui_mode` reset first. The live fingerprint (`current_edit_fingerprint`) builds them from the Setup fields with `connection_settings_from_setup`, as Save and autosave do. On Open, the baseline is now taken after the loaded settings are copied into the Setup fields; taking it before would have flagged every freshly opened show as unsaved. Tests: `edit_fingerprint_tracks_edits_only` (console IP, sync direction and allowlist changes count; pacing and UI mode don't) and `unsaved_check_is_stable_until_an_edit`.

### R3 — `inf` typed into a sidecar Linear taper breaks the show file (Medium)

**Where:** [src/ui/sidecar_tab.rs:817-825](../src/ui/sidecar_tab.rs#L817-L825); `taper_to_value` in `src/model/sidecar.rs`.

**Problem:** `egui::DragValue::new(min)` and `new(max)` have no `.range()`. egui's default parser accepts "inf", and "nan" ends up as +inf after clamping. Every hardware move then computes NaN. The `ConsoleTx` backstop keeps it off the desk, but raw-OSC bindings send it to external targets. Worse, the show saves `"max": null`, which `Taper` can't read back, so the show and every later autosave fail to load as "corrupt". This is the gap left in H3.

**Fix:**
- Add `.range(...)` to both `DragValue`s with sensible finite bounds.
- Reject non-finite values in `taper_to_value`.
- Give `Taper::Linear` a null-tolerant or finite-validating deserializer, like the one `CategoryTiming` got.

**Verify:** a test that a show with `"max": null` in a Linear taper still loads.

**Status: fixed.** Both `DragValue`s have a `±TAPER_LIMIT` (1e6) range, so egui clamps a typed `inf` or `nan` to a bound. `Taper` loads through a `TaperRepr` mirror with optional bounds: a `null` or missing bound takes its default (0..=1, or 10 dB for `FaderDb`), and all bounds are clamped to the limit. `taper_to_value` and `taper_to_norm` work on `Taper::sanitized()` and treat a NaN position as 0, so their output is always finite; a NaN position on a fader gives −inf, never unity. Tests: `sidecar::non_finite_taper_bounds_are_contained` and `show_file::a_null_taper_bound_still_loads`.

### R8 — Concurrent saves share one `.tmp` file (Low-Medium)

**Where:** [src/persistence/atomic_write.rs:22-30](../src/persistence/atomic_write.rs#L22-L30). The tmp path is always `<path>.tmp`.

**Problem:** The new Save-from-prompt flow makes overlapping saves reachable: a Save still in flight, then Close, then Save in the prompt. Both writers truncate, write and rename the same file, which can leave mixed JSON that is reported as "Saved". The untitled autosave folder is also shared by every instance and session (stem `untitled`, [src/persistence/backup.rs:153-159](../src/persistence/backup.rs#L153-L159)), so two instances prune each other's autosaves and can collide on one filename.

**Fix:**
- Use a unique temp name per write (append pid plus a counter or random suffix), and still remove it on failure.
- Add a per-session id to the untitled stem.

**Status: fixed.** Each write uses its own temp file, `<path>.<pid>-<n>.tmp`, which is still removed on failure. `overlapping_saves_each_land_whole` runs eight 1 MB saves of one file at once; with the shared name it fails every time (a rename finds its temp file already moved away). Untitled autosaves now use a per-run stem, `untitled-<start time>-<pid>`. A per-run stem alone would leave every run's series behind for good, so an untitled autosave also prunes older runs, keeping the `KEEP_UNTITLED_SESSIONS` (10) most recent including the current one. The single shared `untitled` series from older builds counts as one of those runs. Test: `untitled_runs_keep_their_own_series`.

### R9 — Autosave failures are silent and not retried (Low-Medium)

**Where:** `AutosaveCompleted` handling around [src/ui/app.rs:1461](../src/ui/app.rs#L1461) and [:2058](../src/ui/app.rs#L2058).

**Problems:**
- The new fingerprint is stored even when the write failed, so after a full-disk failure the autosave isn't retried until the next edit, and nothing is shown.
- After recovering from a backup, the recovered content becomes the "saved" baseline ([app.rs:1333](../src/ui/app.rs#L1333)) while the original file on disk is still corrupt. Quitting without "Save recovered to original path" gives no prompt.

**Fix:**
- On failure, keep the previous fingerprint and show a status message.
- Don't set the baseline when the file that was loaded isn't the file future saves will go to.

**Status: fixed.** `AutosaveCompleted` carries an `error`. After a failed write (or a failed serialize), the task reports the previous fingerprint, so the next interval tries again, and the UI shows "Autosave failed: …". A show recovered from a backup gets a baseline no show matches (`mark_unsaved`), so leaving without saving it asks first.

## Priority 4 — hardware (sidecar and Stream Deck)

### R2 — Motor echoes on 14-bit faders now cancel fades (Medium)

**Where:** `absolute_v14` in [src/console/sidecar_service.rs:548-556](../src/console/sidecar_service.rs#L548-L556), used by the echo check at `:286-304`.

**Problem:** `absolute_v14` returns `None` for `ControlMode::Absolute14` (CC MSB/LSB pairs), so motor echoes on those bindings are never suppressed. Since the H7 fix, every hardware value runs `inbound::apply_operator_change`. An unsuppressed motor echo can therefore cancel a running fade on that parameter, mark it dirty, drive gangs and be recorded by macro learn.

**Fix:** assemble the Absolute14 MSB/LSB pair into a v14 value and apply the same `motor_echo` matching as for PitchBend/Absolute7. Also give Absolute14 the motor dedup (the `:548` path), which it currently lacks.

**Status: fixed** (not yet tried on hardware). For an Absolute14 binding, the echo check now runs after decoding, on the assembled value, using the same `is_motor_echo` test and tolerance (16) as pitch bend. A genuine move records the fader's position, so the motor poll dedups against where the fader really is. Test: `a_14_bit_motor_echo_is_not_a_hand_move` (the echoed pair doesn't reach the console; a real move right after does). It fails without the fix.

**Related (Low-Medium):** for the first 2.5 s of a memory recall (`in_console_load`), sidecar moves skip the whole operator-change chain ([src/console/inbound.rs:160-240](../src/console/inbound.rs#L160)). A D700 grab then doesn't cancel the fade, doesn't reach gangs and isn't learned. Sidecar-originated changes are unambiguous, so let them bypass the console-load gate.
**Status: fixed.** The gate now applies only when `source != InboundSource::Sidecar`. Test: `inbound::a_sidecar_move_during_a_console_load_is_the_operator` (dirty mark, gang sibling and learn step all happen with the load window armed).

### M19 remainder — motor behaviour (Medium)

- **Full-travel slam:** the initial sync with an unknown fader position still sends one full-travel command ([sidecar_service.rs:575-578](../src/console/sidecar_service.rs#L575-L578)), the end-stop slam from field note 23. Ramp from mid-travel, or ramp from the first reported position.
- **Stale position after reconnect:** `fader_pos` survives a MIDI reconnect, so ramps start from a stale position. Clear it on reconnect.
- **Ramps outlive their binding:** they keep running while the sidecar is disabled and after a binding is deleted, disabled or edited (`advance_ramps` at `:236`, `:610`; `sync_surface` at `:659-685`). Clear ramps on disable, on binding edits and in `sync_surface`.
- **Ramp echo window hides hand moves:** on boards without touch sensing, reports anywhere in the ramp's range are dropped for 300 ms after the last step (`:593-604`, `:297-300`). A real hand move in that window is lost, and a move outside the range doesn't cancel the ramp. Cancel the ramp on a report outside the expected path.

**Status: fixed** (none of it tried on the D700 yet):
- *Slam:* a fader whose position is unknown now counts as being at mid-travel (`MOTOR_UNKNOWN_POS`), so a long move to it is ramped from there. At most about half the travel goes in one command, and the approach to an end stop is always stepped.
- *Reconnect:* the UI now sends a new `SvcCmd::SurfaceReconnected` on a sidecar MIDI connect. It forgets fader positions, ramps, echo windows and held touches, then syncs. A plain `SyncSurface` (show load, binding add, the Sync button) keeps positions, since the device didn't change.
- *Ramps outliving bindings:* each tick drops a ramp whose binding is gone, disabled, no longer motorised, or has a different control or mode, and all ramps while the sidecar is off. `sync_surface` clears ramps before driving the motors afresh.
- *Hand moves:* a report outside the echo range (a hand move) now also stops that fader's ramp. Reports inside the traversed range are still taken as echo for 300 ms. Narrowing that needs the real device's report lag, so it waits for a D700 session.
- Tests: `a_reconnect_forgets_fader_positions`, `switching_off_stops_a_ramp`, `deleting_the_binding_stops_its_ramp` and `a_hand_move_stops_a_ramp`. `console_change_pushes_motor_but_own_echo_does_not` now checks the first command is a step from mid-travel. The behaviour tests fail with their fix undone.

## Priority 5 — Android app (`monitor_android/`)

Paths below are relative to `monitor_android/app/src/main/java/com/pob31/s21monitor/`.

### R5 — Battery drain when the daemon never answers (Medium)

**Where:** `service/MonitorService.kt:276-291` (the heartbeat renews the wake lock) and `:319-340` (`holdAwake`, and the Wi-Fi lock with no timeout).

**Problem:** The wake lock is renewed whenever the link is running, whether or not the daemon answers. A phone left on "No reply", "Name not recognised" or "Lost" after the show holds a partial wake lock and a Wi-Fi lock, and pings every 2 s, all night.

**Fix:** renew the locks only while `connected`, or release both and back off the pings after a few minutes of no reply.

**Status: fixed** (unit-tested; not yet run on a phone). The rule is `LinkTracker.keepAwake`: stay awake while the link is up, and for `AWAKE_GRACE_MS` (5 min) after it was last up, or after it began. It turns on "up", not "any reply", because a daemon that doesn't know the name does reply. Past the grace, the heartbeat releases both locks and pings drop from every 2 s to every 15 s. The link coming back takes the locks again at once (in `refreshLink`), not at the next heartbeat. Tests: `LinkTrackerTest.theAwakeGraceRunsFromWhenTheLinkWasLastUp` and `aRefusedNameDoesNotKeepThePhoneAwake`.

### Android Lows

- **`refreshLink` race:** it runs on two IO threads (the inbound loop and the watchdog) as an unlocked check-then-update ([MonitorService.kt:303-312](../monitor_android/app/src/main/java/com/pob31/s21monitor/service/MonitorService.kt#L303)). A stale LOST can overwrite a fresh connected state, locking the controls for up to 1 s. Publish the status from one coroutine, or under a lock.
  **Status: fixed.** `refreshLink` is `@Synchronized`, and so are the lock helpers it now calls.
- **`onTimeout` leaves a blank state:** after `onTimeout` the UI shows "Connecting…" with no banner and no watchdog (`:177-191`). It can't happen with `connectedDevice`, which has no time limit, but set a problem value anyway.
  **Status: fixed.** A new `LinkProblem.STOPPED` shows "Android stopped the monitor link. Disconnect, then connect again."
- **Early `stopSelf()`:** when `goForeground()` fails, `stopSelf()` runs before any `startForeground` (`:128-133`). On some Android versions this raises "did not then call startForeground". *(Unconfirmed.)*
  **Status: left as is.** Still unconfirmed. From the foreground `startForegroundService` succeeds and `startForeground` doesn't throw. The failing case is a sticky restart, which isn't started through `startForegroundService`, so the "did not call startForeground" rule shouldn't apply.
